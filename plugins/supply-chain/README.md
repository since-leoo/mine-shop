# 供应链插件

`since/supply-chain` 将芸众供应链的选品、商品同步、采购订单、采购售后和执行日志封装在插件内。协议来自 `store513/plugins/yz-supply` 的调用扫描，SDK 按商品、选品、报价、订单、售后和消息拆分能力接口。

商城商品、SKU、下单、支付、库存预占和客户退款继续使用主项目流程；插件仅通过公共 Contract 和集成事件衔接，保留自己的上游商品快照、映射、采购单、采购售后及任务日志。商品来源标记为 `supply_chain`，供应商账号、上游 SKU 与版本信息在下单时冻结。

自有异常使用 `app/Infrastructure/Error/SupplyChainError.php` 的 `400xxx` 业务码与中文模板；供应商状态码和任务恢复协议码保持原值，具体位置与回归入口见[异常与协议错误码说明](ERROR-CODES.md)。

## 安装与启动

依赖本项目的 PHP 8.2+、Swoole、MySQL、Redis 和现有 Composer/前端依赖。请先按主项目说明配置数据库、Redis、HTTP 服务和前端构建环境。下列命令在项目根目录执行，迁移和安装命令会修改当前环境数据库。

1. 生成一份部署密钥，保存在部署环境变量或受保护的 `.env` 中：

   ```bash
   php -r 'echo base64_encode(random_bytes(32)), PHP_EOL;'
   ```

   ```dotenv
   SUPPLY_CHAIN_ENCRYPTION_KEY=上一步生成的Base64字符串
   ```

   这是 32 字节随机值的 Base64 编码，供本地 AES-256-GCM 凭证加密使用，和供应商 `AppSecret` 不同。所有 Web、队列进程及服务节点必须使用同一份密钥。密钥为空或格式错误时不能保存有效凭证；已有凭证不能通过直接更换此变量完成轮换，否则将无法解密。请随数据库备份妥善保存原密钥，不提交版本库。

2. 执行核心迁移，再安装新插件：

   ```bash
   php bin/hyperf.php migrate
   php bin/hyperf.php plugin:install since/supply-chain
   php bin/hyperf.php plugin:list
   ```

   安装流程执行 `Database/Migrations` 和 `Database/Seeders`，成功后生成 `install.lock`。插件需同时满足 `plugin.json` 中 `enabled: true` 和存在 `install.lock` 才会加载 ConfigProvider、控制器、监听器、定时任务和队列进程。检查安装输出及日志中的迁移、权限填充结果。

   已安装环境升级使用标准迁移和权限填充命令：

   ```bash
   php bin/hyperf.php migrate
   php bin/hyperf.php plugin:seed since/supply-chain
   ```

   项目已将已安装插件的迁移路径接入标准 `migrate`。更新有业务数据的插件无需 `plugin:install --force`；该选项会先走卸载流程。

3. 由权限管理员给相应角色分配 `supply-chain:*` 下的具体权限，重新登录或刷新权限。Seeder 幂等注册隐藏权限组和按钮权限，不自动给任何角色授权。

4. 按项目部署方式重建并发布 `web` 前端，重启 Hyperf 服务及工作进程。开发环境启动入口：

   ```bash
   php bin/hyperf.php start
   ```

   启动入口会检测已安装、启用插件的清单变化，自动重建注解扫描及 AOP 缓存；`APP_DEBUG=false` 时新插件路由也会随重启更新。前端入口先检查后端安装状态，未安装或停用时显示提示，可点击“刷新插件状态”重新检查。

   后台入口为“插件中心 → 供应链”。前端桥接文件是 `web/src/plugins/since/supply-chain/index.ts`，实际页面位于本插件 `web/` 目录。API 前缀为 `/admin/supply-chain`，使用现有登录鉴权和权限中间件。

## 连接配置与运行模式

在“连接设置”中新建连接，填写名称、API 域名、`AppKey`、`AppSecret` 和运行模式。API 域名只填写 HTTPS origin，例如 `https://supply.example.com`，不带 `/supplyapi`、其他路径、账号、查询串或片段；当前默认 API 前缀为 `/supplyapi`。

新连接默认“暂停新业务”，先保存，再执行“测试连接”。测试会真实读取上游商品接口，成功说明本次认证及商品接口请求完成，不代表订单和售后协议已验证。编辑连接时 `AppSecret` 不回显，留空保留原值，填写新值后更新凭证版本及缓存隔离。已有商品映射或采购记录的连接不能直接更换账号或域名，需新建连接。

| 模式 | 新选品导入及新下单 | 已有同步、采购履约、查单和售后 |
| --- | --- | --- |
| `active` 运行中 | 允许 | 继续处理 |
| `pause_new` 暂停新业务 | 拒绝 | 继续处理 |
| `draining` 仅处理存量 | 拒绝 | 继续处理 |

当前 `pause_new` 与 `draining` 的执行限制相同，后者用于标记退出供应商时的运营意图；不会在存量结束后自动卸载或删除历史数据。处理存量期间应保持插件和连接可用。

高级设置支持“退货物流映射”JSON：键为商城使用的物流公司名称，值为供应商提供的名称与 `company_code`。空映射为 `{}`。下面仅展示结构，实际名称和代码须由供应商提供，不能猜测：

```json
{
  "本地物流公司名称": {
    "name": "供应商物流公司名称",
    "code": "供应商明确提供的编码"
  }
}
```

后端仅接受并返回 `settings.return_carriers` 白名单字段；缺少映射或编码时，退货物流任务会失败并记录原因。

## 选品与商品同步

1. 选择连接，在“选品中心”搜索、分页浏览或打开详情。详情只读取上游数据；上游选品状态无法确认时显示未知，不当作“未选品”。
2. 跨页勾选商品，每批最多 50 件，填写本系统有效的商品分类 ID 和售价倍率（1–10）。切换连接会清空已选商品。
3. 提交后只表示任务已持久化，需在“任务与重试”查看每件商品的执行结果。导入流程处理上游选品，再拉取商品和 SKU 并建立本地映射。
4. 新导入商品默认是商城商品表中的**草稿**。进入原商城商品管理检查分类、规格、内容、售价和库存后，再通过原流程发布。初始售价取上游建议售价与“供货价 × 倍率”两者较大值，金额在接口及存储中为整数分，页面转换为元显示。
5. “已导入商品”显示本地商品 ID、上游 ID、绑定及同步情况，可单独发起同步。默认不覆盖运营修改过的标题、内容和销售价；供货快照、SKU 可用性和库存投影继续更新。供应商下架或删除规格时，相关可售能力会受限。

库存通过核心库存接口投影到商城，核心 Redis/Lua 预占、扣减和释放流程继续生效；不能将一次上游库存快照直接当作不含本地预占的可售库存覆盖。任务并发及过期同步结果通过版本和租约约束处理。

## 采购订单、结果未知与售后

客户支付及订单事件通过公共事件/能力接口触发插件采购任务。后台“采购订单”可查看商户采购号、上游订单及订单行，再提交查询任务。库存、价格和运费检查仍可能被供应商拒绝，应以任务和接口日志的具体原因处理。

网络超时、进程中断或返回结果不确定时，写任务可能进入 `unknown`。系统会安排查询；管理员也可在采购单中选择“查询上游结果”。**未知结果不可直接重试下单或重复申请采购售后**。查询仍无法确认时，使用商户采购号/上游订单行联系供应商核实，页面不提供猜测成功或直接重建采购的按钮。

供应商明确拒绝、或确定请求尚未发送时，会持久化 `order_release_protection` 本地补偿任务。即使 Redis 暂时故障，也能恢复解除库存保护，原推单失败原因不会被清理错误覆盖。该补偿不调用供应商，连接停用后仍可执行；遇到后续提交中、结果未知或已受理的采购会跳过，避免解除新请求的保护。

“采购售后”与商城客户退款各自保留状态。客户售后事件先形成待审核记录，管理员需选择上游订单行、读取该行售后政策，再明确填写数量、退款金额（分）、原因类型、收货状态、退款类型和退款方式等上游编码。页面不会自动猜测编码，当前不支持换货 `refund_type=2`。提交成功仅表示供应商售后任务进入处理，客户退款仍由原商城售后审核及支付退款流程决定。

按采购行查询得到的候选售后编号只供人工核对，不自动认领，不据此提交取消或退货；详情中明确标注候选身份，状态继续保持未知。已有明确上游售后号的客户取消、退货物流等事件由插件队列继续处理，失败原因在日志中可查。

旧插件扫描结果未确认**普通采购订单直接取消**协议。当前 SDK 对该操作显式拒绝并记录错误，不能拿云仓订单取消接口替代，也不能把商城订单取消当成供应商取消已完成。应核实采购状态并按供应商已支持的售后流程处理。

## Redis 队列与定时调度

`ConfigProvider` 注册以下专用队列，各自有一个消费进程，使用默认 Redis 连接池及协程并发：

| 队列 | 任务 | 每进程并发上限 |
| --- | --- | --- |
| `supply_catalog` | 选品导入、商品同步 | 2 |
| `supply_order` | 采购推送、查询及订单动作 | 4 |
| `supply_after_sale` | 采购售后申请、查询及动作 | 2 |
| `supply_message` | 消息拉取、确认与连接数据刷新 | 2 |

Hyperf `supply-chain-dispatch` 定时任务每分钟执行，调度数据库任务、恢复过期租约、补投队列并检查遗漏的已支付订单。每个启用连接每分钟安排消息拉取，商品和采购周期刷新使用五分钟业务去重窗口。现有 `config/autoload/crontab.php` 的 `enable` 必须为 `true`，主进程配置需保留 `CrontabDispatcherProcess`。

数据库是持久任务依据；Redis 队列消息只携带任务 ID 和投递版本，不携带凭证或收货地址。队列 Job 的框架重试关闭，自动退避、最大次数、人工重试和未知结果查询由插件任务状态控制，避免两套重试机制重复提交。任务提交后可能要等待下一次分钟调度。

正常 Hyperf 服务启动会拉起已注册的消费进程和定时调度进程，无需另设系统 cron 来调用 HTTP。多节点部署共享数据库、Redis 和部署密钥。若任务长期待执行，先检查插件安装状态、进程是否加载、crontab 配置、Redis 连接、数据库任务的投递事件及服务日志。

## 日志与权限

“任务与重试”保留任务类型、业务键、状态、累计次数、每次执行记录、失败原因和操作事件。普通可重试失败可以在修正原因后人工重试，必须填写本次重试原因；历史 attempt 及审计事件保留。未知结果不能用此操作重复发送。

“接口日志”记录上游操作、关联任务/attempt、请求追踪号、HTTP 和供应商状态、耗时、参数及结果。参数和结果经过脱敏，错误信息也经过处理；`AppSecret`、token、签名等敏感值不展示，电话、收货地址等个人信息被屏蔽。JSON 作为文本渲染，不执行供应商返回的 HTML。

| 权限 | 作用 |
| --- | --- |
| `supply-chain:connections/read,update,test` | 查看配置、修改配置、测试连接，分别授权 |
| `supply-chain:catalog/read,import` | 查看选品、导入商品，分别授权 |
| `supply-chain:products/read,sync` | 查看映射、发起同步，分别授权 |
| `supply-chain:purchases/read,query` | 查看采购、查询结果，分别授权 |
| `supply-chain:after-sales/read,submit,query` | 查看采购售后、提交申请、查询结果，分别授权 |
| `supply-chain:tasks/read,retry` | 查看任务和执行摘要、人工重试，分别授权 |
| `supply-chain:logs/read` | 查看接口日志摘要 |
| `supply-chain:logs/params` | 额外允许查看已脱敏参数，不授予原始敏感数据访问 |

表中逗号表示多个独立权限码，例如 `connections/read` 与 `connections/update`。任务参数接口需同时具备 `tasks/read` 和 `logs/params`，接口日志详情需同时具备 `logs/read` 和 `logs/params`。普通任务详情不会返回 payload、结果和 attempt 参数；没有参数权限仍可排查失败摘要。后台没有解密查看 AppSecret 的入口。

## 验证范围

可在项目根目录运行无需业务数据库/Redis的单元测试：

```bash
php vendor/bin/phpunit -c phpunit.unit.xml tests/Unit/SupplyChain
```

前端隔离回归使用本地 mock API，包含真实插件中心入口、选品、失败重试、日志权限和售后候选号行为。在 `web` 目录执行：

```bash
node node_modules/@playwright/test/cli.js test --config tests/supply-chain/playwright.config.ts
node node_modules/vue-tsc/bin/vue-tsc.js --noEmit -p tests/supply-chain/tsconfig.json
```

测试覆盖协议构造、凭证加密、状态机、权限边界、路由与队列配置装配及页面交互。**尚未使用真实供应商 API 完成联调**，本地测试通过不能证明供应商当前账号的权限、返回字段、售后编码及业务限制一致。正式启用前需要使用供应商测试账号逐项核对选品、报价/运费、采购推送与查单、发货、退款政策、退货物流和消息确认，并实际验证部署环境的数据库迁移及队列运行。
